# Automation Pipeline Learnings

Repo-specific learnings captured by automation-pipeline runs (skills/agents under `.ai/`). Append new, non-obvious, reusable lessons here — one bullet each, with the evidence that surfaced it.

- **[NON-NEGOTIABLE] When a skill or agent actually runs a testcase (`npx playwright test ...`), never run it inside the default command sandbox — run it with the sandbox override from the start.** The sandboxed shell's filesystem and network restrictions produce failures that look like real test/app failures but aren't: a Chromium `ProcessSingleton`/profile "Operation not permitted" error (browser can't launch/write its profile dir) and a DNS `getaddrinfo ENOTFOUND <host>` error (network calls to hosts outside the sandbox's allowlist, e.g. anything but `registry.npmjs.org`, are blocked outright). Both were hit and had to be re-run outside the sandbox to get a real pass/fail signal (see the `@homepage-heading-and-get-started-link` UI run and the `@api-fetch-user-by-id`/`@api-create-user` API runs). Don't try sandboxed first and fall back on failure — that wastes a run and risks a sandbox artifact being misread as evidence. Any test execution (via `debug-a-testcase` or any other skill/agent step that runs Playwright tests) should go straight to the sandbox override.
- **Check installed tool versions before trusting a plan's example config values.** During the initial framework scaffold, three separate version-skew issues surfaced (ESLint config format, TypeScript `moduleResolution` deprecation, and a Jenkinsfile Docker image tag pinned to an older Playwright version than what's actually installed/locked). Before finalizing any config file that pins or assumes a tool version (Docker image tags, `moduleResolution`, ESLint config format, etc.), cross-check against the actually-installed version in `package.json`/the lockfile rather than copying a plan's example verbatim.
- **This repo's ESLint (9+, currently 10.x) only supports flat config.** Use `eslint.config.mjs`, not `.eslintrc.cjs`/`.eslintrc.json` — the legacy format was removed in ESLint 9. Any future plan that specifies a legacy `.eslintrc.*` file name should be implemented as flat config instead.
- **`npm init playwright@latest`'s `--gha` flag is presence-only (boolean).** There is no `--gha=false` form — to skip generating a GitHub Actions workflow (e.g. when the CI target is Jenkins/GitLab/Azure DevOps), simply omit the flag entirely rather than trying to pass a falsy value.
- **No Sonar server/token is configured in this repo yet.** `code-quality-agent`'s scan (SonarQube/SonarCloud/Sonar Scanner) will block on first run until an SDET supplies a server URL/org key and `SONAR_TOKEN` via an environment variable (never paste a token in chat). Until that's set up, treat a Sonar-gate skip as expected rather than a pipeline defect, and fall back to the ESLint + manual code-review gate as the quality signal.
- **When adding tests for a new target site/app, add a dedicated `<SITE>_BASE_URL` env var in `config/env.ts` instead of repointing the shared `BASE_URL`.** `playwright.config.ts`'s UI projects (`chromium`/`firefox`/`webkit`) share one `baseURL` across all specs, and other suites (e.g. `tests/ui/example.spec.ts`) already depend on the existing `BASE_URL` pointing at their own target. Introduced when adding the SauceDemo slice (`SAUCEDEMO_BASE_URL`) — follow the same pattern for any future third-party/demo site added to this repo rather than overwriting the shared var.
- **When building a navigation URL from a `<SITE>_BASE_URL`-style env var, don't raw-concatenate a path onto it (e.g. `` `${env.X_BASE_URL}inventory.html` ``).** That only works if the env value happens to already end in `/`, which the Zod schema (`z.string().url()`) doesn't enforce — flagged in SauceDemo review cycle 1. Follow the existing `authenticatedPage` fixture's safer join pattern (`` `${env.BASE_URL}/path` ``, explicit separator) or normalize the trailing slash before use.
- **Agents explore with `playwright-cli`, which removes the need for hand-written exploration files.** Codegen only records a human's clicks, so earlier runs without a human (SauceDemo) hand-wrote a substitute file. The CLI prints the Playwright code for each action an agent takes, so that output is the evidence. `npx playwright codegen` is no longer used (see `ui-automation-workflow.md`).
- **Running actual headed/live Playwright browser tests in this sandboxed shell can hit a Chromium `ProcessSingleton`/profile permission error that is a sandbox filesystem restriction, not a real test failure.** Symptoms are "Operation not permitted"/"Permission denied" errors tied to the browser's profile directory. Confirm it's sandbox-caused (not a genuine bug) before spending time debugging the test itself, then rerun with the sandbox override to get a real pass/fail signal.
- **A `getByRole('heading', { name: /regex/i })` locator with no `level` scoping is fragile against a page that grows more headings matching that regex over time** — especially on a third-party/external site outside this repo's control. `pages/example.page.ts`'s `heading` locator (matching the `playwright.dev` homepage's `/playwright/i`-named heading) started throwing a strict-mode violation once the live site added three `<h3>` feature-card headings ("Playwright Test"/"Playwright CLI"/"Playwright MCP") alongside the original `<h1>` hero heading — all matching the same loose regex. Fixed by adding `level: 1` to scope to the intended hero/heading-tier element, keeping the regex (not hardcoding today's exact copy) since text drift is a separate, already-documented risk. When writing a heading locator by accessible-name regex against any page (and especially a third-party one), scope by `level` (or another discriminating role option) up front rather than relying on the regex alone to stay unique.
- **Implementation/review verification steps that run `tsc --noEmit` and `eslint` should also run `npx prettier --check` on changed files — ESLint passing does not guarantee Prettier compliance.** Surfaced in the SauceDemo network-interception review (cycle 1): both touched lines in `login.spec.ts`/`cart.spec.ts` failed `prettier --check` (over the `.prettierrc` `printWidth`), and the issue turned out to be repo-wide/pre-existing (41 files fail `prettier --check` repo-wide) rather than introduced by that change — but the implementation summary's verification section never ran Prettier at all despite it being a declared quality gate in this repo. Add a Prettier check alongside typecheck/lint in any future implementation or review verification pass so gaps like this are caught (or at minimum knowingly reported) rather than silently missed.
- **`@api-fetch-user-by-id` and `@api-create-user` (`tests/api/example.spec.ts`, "Users API") cannot pass in this environment as currently configured, and this is not a code defect.** Both go through the worker-scoped `authToken` fixture, which `POST`s to `${API_BASE_URL}/auth/login` before every API test (by design — see `docs/plans/framework-setup-plan.md` §6a, and both tests' own requirements docs list a successful login as an explicit acceptance criterion, not incidental plumbing). The locally configured `API_BASE_URL` (gitignored `.env`) is `https://jsonplaceholder.typicode.com` — a public fake/demo REST API that supports `/users` but has **no authentication layer at all**, so `/auth/login` genuinely 404s there (confirmed via a real, unsandboxed HTTP response, not a network artifact). This is an infrastructure/environment gap — the test file's own header comment already predicted it ("point it at a backend that implements `/auth/login` and the `/users` resource"). A self-healing run on either tag investigated and confirmed there is no legitimate code-level fix: the SauceDemo-style "give it a dedicated `<SITE>_BASE_URL`" precedent doesn't apply (no other spec shares `API_BASE_URL`, so there's no collision to resolve — just the same unresolved "what real backend?" question under a new name), and bypassing/mocking the auth fixture would mean silently dropping a documented precondition rather than fixing anything. Do not attempt to code-fix this again on a future run — it needs an SDET to point `API_BASE_URL` at a real backend implementing both `/auth/login` and `/users` (locally in `.env`, and via the Jenkins `credentials('qa-api-base-url')` binding in CI per `docs/plans/framework-setup-plan.md` §8) before either test can be expected to pass.
- **A browser launched inside a setup-project test cannot be shared with the dependent project's workers: it dies with the setup worker.** Playwright 1.62.1 runs the `setup_<project>` test in its own worker (different worker hash), tears that worker down before the dependent project's workers start, and playwright-core's exit handler kills every browser that worker launched, so `browserType.connect(wsEndpoint)` from a later worker fails with `ECONNREFUSED` (prototype P-0 in `docs/plans/shared-browser-per-project-plan.md` §3). To share one browser per project across workers, the setup project must spawn a **detached** helper process that owns `launchServer` and publishes its endpoint out-of-band (the repo's pattern: `fixtures/shared-browser/browser-server.mjs` + a state file under `os.tmpdir()`, consumed via a worker-scoped `connectOptions` override in `fixtures/index.ts`), with a `teardown_<project>` project to stop it.
- **Teardown projects never run when the runner is interrupted (Ctrl+C/SIGINT, SIGTERM, SIGKILL, `--global-timeout`), so anything a setup project spawns detached must watch the runner pid itself.** Verified in plan prototype P-6/P-7 and independently in `docs/reports/shared-browser-per-project-review-cycle-1.md` (SIGKILL of the runner's process group → 0 teardown lines, yet the `browser-server.mjs` runner-pid watchdog left 0 servers/browsers within 4 s; the next setup removed the stale state dir). Also on macOS, WebKit's `launchServer().process()` is a `bash` launcher wrapper, so kill/crash logic must signal the **process group** (`process.kill(-pid, ...)`), not the pid (prototype P-3).
- **CLI `--grep`/`--grep-invert` do not filter dependency (setup/teardown) projects in Playwright 1.62.1 — only project-level `grep` does.** `setup_*`/`teardown_*` still run whenever a selected test's project depends on them, even if their own tests don't match the CLI grep, and drop out when no dependent test is selected (`--project=api`, `--grep @api`). Don't rely on the CLI grep to keep setup/teardown tests out of a run; give each setup/teardown project its own file (`testMatch`) with one test that derives its target from its own project name (see `fixtures/shared-browser/projects.ts`), or use a project-level `grep`. Evidence: `--list --grep-invert @framework` in `docs/reports/shared-browser-per-project-review-cycle-1.md` §2.
- **`eslint.config.mjs` only configures rules for `*.ts`, so any `.mjs`/`.js` file (e.g. `fixtures/shared-browser/browser-server.mjs`) is linted with no rules — "ESLint 0 errors" says nothing about it.** For JS helper scripts in this repo, rely on `// @ts-check` + `tsconfig.json` `allowJs`/`checkJs` (and avoid top-level `await`, which fails TS1378 under `module: commonjs`), or add an `**/*.mjs` ESLint block (CQ-1 in `docs/reports/code-quality-2026-09-30.md`). Separately, the repo-wide Prettier backlog noted above is now cleared: `npx prettier --check .` reports 0 non-compliant files as of that report.
- **Orchestrators: snapshot the SDET-owned uncommitted config lines (e.g. `workers`/`retries` in `playwright.config.ts`) at run start and re-check them before review.** In the `shared-browser-per-project` run 2, CI `workers`/`retries` read `5`/`2` at start and `2`/`1` by stage C without any agent claiming the edit (`docs/reports/shared-browser-per-project-orchestration-log.md`); pipeline agents must leave such lines untouched and surface the drift to the SDET rather than "correct" it.
- **To share one resource (e.g. a browser) across several Playwright projects, make them all depend on ONE setup project and key the resource by what they share (the engine), not by project name.** Playwright runs a setup's `teardown` project only after every project depending on that setup has finished, so one `setup_<engine>`/`teardown_<engine>` pair safely serves `webkit` and `new_webkit` together. Keying state by project name instead silently started a second WebKit for `new_webkit` (two server pids in the setup log). Since the projects share one browser process, only per-context settings (viewport, user agent, `isMobile`) may differ between them; launch settings (`channel`, `headless`, `launchOptions`) must match, which `sharedBrowserProjects()` enforces at config load. Evidence: `@framework` run with `webkit` + `new_webkit` → one `setup_webkit` log line `for projects webkit, new_webkit`, one server pid, 38/38 passed.
- **Attach to a `--debug=cli` test run with the local CLI (`npx --no-install playwright cli attach tw-XXXXXX`), not the global one.** Global `playwright-cli` 0.1.23 against Playwright 1.62.1 fails on `attach` and `snapshot` with `TypeError: Cannot read properties of undefined (reading 'tools')`; the local CLI works. The debug output literally prints `playwright-cli attach ...`, so don't copy it verbatim. The local CLI lacks `recording-*`, emulation and `webmcp-*` commands, which is the only reason to use the global one, in a standalone session. Standalone `open`, `snapshot`, `run-code` and `requests` were confirmed on the local CLI; `generate-locator`, `eval` and clicks only on the global one.
- **Check `MUTATION_ENABLED` in the local `.env` when a UI test fails or the run looks wrong.** When `true`, it skips the shared-browser setup projects, filters to `@mutation-target`, and deliberately hides elements, so `@homepage-heading-and-get-started-link` fails with `element(s) not found` on the heading with no defect in the code. Rerun with `MUTATION_ENABLED=false` set in the command's environment before treating such a failure as evidence.
- **Generated locators from `playwright-cli` don't meet repo rules as they are.** `generate-locator` on the `playwright.dev` `h1` returned `getByRole('heading', { name: 'Playwright enables reliable' })`: no `level`, and pinned to volatile copy. Normalize before use (`ui-automation-workflow.md`).
- **API endpoints can be explored in a CLI session through `page.request`.** `run-code` with `page.request.get/post` returned real status and body from `jsonplaceholder.typicode.com` (200 on `/users/1`, 201 on `POST /users`, 404 on `/auth/login`).
- **`--debug=cli` runs headless when `CI=1` is set, and `attach` still works.** The `--help` text says `--debug` implies `--headed`, but on Playwright 1.62.1 the repo's `headless: !!process.env.CI` wins: `CI=1 MUTATION_ENABLED=false npx playwright test --grep @homepage-heading-and-get-started-link --project=chromium --debug=cli` logged `headless=true`, launched `chrome-headless-shell`, and accepted `attach` and `run-code` from the local CLI. `MUTATION_ENABLED=false` is required because the config throws on `CI` with mutation enabled. `CI=1` also applies the config's other CI values to that run (one retry, `on-first-retry` traces).
- **A bare `playwright-cli open` doesn't match the `chromium` test project; `open --device "Desktop Chrome"` does for user agent and viewport.** Bare `open` launched headless system Chrome with a `HeadlessChrome/156` user agent, while `devices['Desktop Chrome']` sends `Chrome/151.0.7922.34` on Windows; a site that varies by user agent can behave differently. With `--device "Desktop Chrome"` the user agent and 1280x720 viewport matched the preset, but the process was still `/Applications/Google Chrome.app`, not the bundled Chromium the tests use, so a real engine difference can remain.
- **`toHaveCount(n)` doesn't prove visibility; when an acceptance criterion says "visible", assert visibility on each element.** On the SauceDemo error state, injecting `.error_icon { visibility: hidden }` left the count at 2 while `isVisible()` was false for both, so a count-only check would still pass (F-1 in `docs/reports/saucedemo-login-suite-review.md`). The gap started in the plan, so plans should word such checks as "count N, each visible".
- **`playwright/expect-expect` doesn't see assertions inside local helper functions, and `npm run lint` has no `--max-warnings`.** Helpers such as `expectLanded` produced one false "Test has no assertions" warning per call site (9 in `tests/ui/saucedemo/saucedemo-login.spec.ts`). The rule's `assertFunctionNames` option fixes this without turning the rule off, but it means editing `eslint.config.mjs`, so plans that use assertion helpers should list that file or accept the warnings. These warnings don't fail CI (F-3 in `docs/reports/saucedemo-login-suite-review.md`).
- **`npx tsc`, `npx eslint` and `npx prettier` can fail with `Cannot find module` in a checkout whose `node_modules/.bin` holds plain files instead of symlinks; this is an environment issue, not a code defect.** Use `node node_modules/typescript/bin/tsc`, `node node_modules/eslint/bin/eslint.js` and `node node_modules/prettier/bin/prettier.cjs`. `npm run lint`, `typecheck` and `format:check` should fail the same way until `node_modules` is rebuilt. `npx --no-install playwright` still works. Evidence: `docs/reports/saucedemo-login-suite-review.md` §1, and re-checked by the orchestrator.
- **On SauceDemo, `performance_glitch_user` reaches `/inventory.html` about 5 s before the page is usable, so a URL check proves nothing for that user.** The title appeared at 5,091-5,107 ms against 50-83 ms for other users, which is right at Playwright's default 5 s assertion timeout. Assert the landing title first, with a longer timeout for that test only (`docs/exploration/saucedemo-login-suite-exploration.md` E-8, `docs/reports/saucedemo-login-suite-review.md` §1).
- **`generate-locator`, `eval`, `click` and `fill` also work on the local CLI (1.62.1), not only the global one, and `run-code` has no `URL` global.** `new URL(...)` inside `run-code` throws `ReferenceError: URL is not defined`. Evidence: the `saucedemo-login-suite` planner's stage report; the `URL` error is not recorded in its exploration file.
- **Two lint and type constraints for page objects and data-driven specs:** a page object field can't be named `title` because it clashes with `BasePage.title()` (`TS2416`), and a tag array held in a variable fails `playwright/valid-test-tags` unless spread as `{ tag: [...tags] }` (D-1 and D-2 in `docs/reports/saucedemo-login-suite-implementation-summary.md`).
- **On SauceDemo, the cart badge element (`[data-test="shopping-cart-badge"]`) is absent from the DOM entirely when the cart is empty — it is not present-with-text-"0" or present-but-hidden.** Confirmed live: the empty-cart snapshot has no badge node at all, and only the cart link's `aria-label` (`"Cart, empty"`) signals the empty state; after adding one item, the badge appears with text `"1"` and the link's `aria-label` becomes `"Cart, 1 items"` — literally "1 items", not the grammatically expected "1 item" (confirmed verbatim via `run-code`, not assumed). Assert on the badge's presence/text for a non-empty cart rather than expecting `toHaveText('0')` or `toBeHidden()` when empty, and don't normalize/assume grammatical accessible-name text. Also, because the cart link's own accessible name carries the dynamic count under test, locating it by `getByRole('button', { name: ... })` filtered on that text would make the locator itself fragile against the value being asserted — use the stable `data-test` locator instead (same pattern as the pre-existing `pageTitle` locator). Evidence: `docs/exploration/saucedemo-cart-add-item-exploration.md` §E-3/E-4/E-6, `pages/saucedemo/saucedemo-cart.page.ts`, `docs/reports/saucedemo-cart-add-item-review.md`.
